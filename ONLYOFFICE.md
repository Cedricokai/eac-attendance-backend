# EAC ONLYOFFICE and sheet-access integration

The EAC toolbar owns employee assignment and policy history. ONLYOFFICE renders and edits the original workbook. No workbook is split, rebuilt from selected sheets, converted to a reduced grid or truncated by the backend.

## Employee workflow

Open the existing workbook, click **Sheet access**, choose a sheet, enable **Limit this sheet to selected employees**, and assign **View only** or **View and edit**. Other employees get **No access**. The dialog searches the existing employee-sharing API and can grant workbook sharing through the existing File Suite service without email. The owner and enabled ROLE_ADMIN accounts retain full control. Assigned employees still need File Management page/system access.

Click **Save assignments and apply**, then **Save workbook**. Commit an active cell edit with Enter before saving. EAC's save button uses the signed Document Server forcesave command; it does not depend on automating the embedded toolbar. Pending policy changes block other employees from opening until the native checkpoint passes validation. All sheet names remain visible in EAC, with a denial panel on a sheet the employee cannot view. Another allowed sheet remains selectable.

File History shows immutable content checkpoints with employee initials, name, save time and Saved status. It refreshes while open. Attribution is explicitly the last editor reported by the signed native callback; a co-editing checkpoint can contain several contributors. Assignment history separately retains the actor and each policy snapshot.

## Enforcement and storage

- V15 adds file_office_sheet_policies and file_office_sheet_policy_audit. Policy updates require owner/manager access plus FILE_MANAGE_ACCESS, validate active employee accounts and grant workbook access only when explicitly requested. Optimistic policy versions reject stale updates. Owner/ADMIN exceptions are mandatory.
- A versioned background plugin uses the official ONLYOFFICE API. It receives a signed configuration with stable eac-{userId} identities and a nonce, and exchanges messages with the EAC page using exact origins, source-window checks and that nonce. No application bearer token is given to the plugin. The employee picker and policy persistence remain in EAC.
- Native EAC_SHEET_ACCESS ranges cover the whole worksheet. Unlisted users get NotView; explicit accounts get CanView or CanEdit. ADMIN repair adds administrator exceptions to existing user-protected ranges. Existing cell-range rules remain separate. A pre-existing password/encryption or native protection the engine refuses to modify requires its owner/password; no encryption or licensing bypass is implemented.
- Every native save checks the workbook's actual stored full-sheet rules against the server policy before appending bytes. An unauthorized/missing/changed rule rejects the checkpoint and preserves previous versions. A native API no-op is not treated as proof of failure: the saved XML remains authoritative.
- Full-file replacement and historical restore require editing permission on every restricted sheet. Employees missing any sheet cannot download the entire workbook (including older versions), copy it, replace its full contents or restore a historical version. Native download/print/copy controls are disabled for these users. Guest links cannot export a workbook with managed restricted sheets. A manual replacement/restoration marks the policy pending until it is reapplied and verified.
- Document Server alone retrieves the whole source through a scoped URL plus a separate server-signed exact-URL header. Browser tokens cannot impersonate that request. Saved cache URLs must match the configured internal or public Office origin and the cache path; fetching is mapped to the trusted internal origin, redirects are refused and bounded macro-free OOXML packages are validated.
- FileContentStore, immutable FileVersion records, existing ACLs, quotas, History, Share and File comments are reused. New valid DOCX/XLSX creation and existing-folder templates use the same upload/copy services. Native DOCX/XLSX/PPTX use the official editor; unsupported formats retain original download. Guest native editing is read-only.
- Shared keys remain stable through checkpoints. Current-access heartbeats and callback contributor checks enforce revocation. Disconnect callbacks allow a short reconnect grace period. Do not restart/upgrade services while users have unsaved documents; save and close first.

These are editor controls plus whole-file export restrictions, not cryptographic isolation of independent sheets. A trusted editor processes the complete workbook, and formulas/drawings can disclose related information. Use separately permissioned files when strict confidentiality outside that editor is required.

## Batch sheet assignment and unchanged uploads (2 November 2026)

Sharing is independent of Office content saving. A freshly uploaded file already has a stored original and can be shared immediately. A native force-save response indicating no changes is now a normal `requested:false` result; the UI reports that the original is already stored. This does not clear pending sheet restrictions or claim an uncommitted cell draft was saved.

In Sheet access, choose a sheet for the starting permissions, select one or more target sheets, assign individual employees or select employees and apply a bulk permission, then Save assignments and apply. The displayed employee assignments replace those on every selected sheet; other sheets are unchanged. The batch endpoint is transactional, preserves owner/admin exceptions, checks optimistic policy versions, reuses existing sharing, and records each changed sheet policy in the audit. Identical policies do not create another revision or pending checkpoint. Unrestricted file sharing does not require a content change.

After the native plugin reports successful application, EAC attempts a force-save with bounded retries while Office synchronizes. Other users remain blocked while the policy is pending; only verification of saved native workbook rules clears pending. If synchronization does not finish, use the native editor Save button and retry Save workbook. No cell content needs to be modified merely to share or assign restrictions.

## Right-click cell locks and offline password downloads (3 November 2026)

Owner/authorized-manager XLSX sessions now expose Lock selected cells and Unlock selected cells in the native right-click menu. Select a rectangular cell range, invoke the action, and enter the existing worksheet password, or create and confirm one for a newly protected sheet. The first-lock dialog explicitly offers to clear other locked-cell formatting so the rest of an unprotected sheet stays editable. Existing protected-sheet lock formatting is retained. A correct password is required to change a protected sheet. The command waits for native protection state, and EAC requests a saved checkpoint; the editor download button waits for the checkpoint before exporting.

The plugin v5 adapter is deliberately pinned to the official Docs 10.0.0 image digest. The public Office API does not expose all standard Locked Cell / Protect Sheet operations. The adapter uses that version's native worksheet-protection commands and its native password preparation code. It fails closed if these interfaces are absent. Retest against an image upgrade before changing the pinned version. The password is transient in the UI/plugin command; it is not written into EAC policy, cell data, custom properties or logs. Native XLSX contains the standard password hash, salt, spin count, cell styles and sheetProtection. Native tests independently verified the SHA-512 hash and wrong/correct-password behavior.

XLSX Download now offers an optional password required to open the offline copy, both in Files and the native editor. Standard sheet/cell protection already saved in the workbook remains present even without this extra option. The separate download password uses Office Agile encryption over a copy of the exact stored OOXML bytes; it does not reconstruct sheets, overwrite the original, change existing protection passwords or retain the opening password. This endpoint reuses normal download permissions and managed-sheet export guards, disallows already-encrypted/non-ZIP packages, and currently caps input at 64 MB. Partial-sheet employees cannot use it to bypass their export restriction.

EAC employee identities and ONLYOFFICE user-protected-range visibility do not work in Microsoft Excel. Keep employee-restricted workbooks online as requested. Authorized whole-workbook exports do not carry EAC identity enforcement; the download dialog explains this. Standard worksheet protection prevents routine edits, while an opening password encrypts the complete downloaded file. Neither recognizes EAC administrator roles offline, and EAC cannot recover a forgotten user-chosen password.

Synthetic native verification produced D2/F2 Locked Cell styles with other cells unlocked and native SHA-512 worksheet protection; wrong-password unlock remained protected and correct-password unlock succeeded. Independent hash calculation matched the exported XML. All 15 command tests and the production frontend build passed. Browser automation was timing out, so a live browser right-click and installed Microsoft Excel UI acceptance check are still required; native generation alone is not a claim of those UI checks.

### Cell menu and employee download controls (2026-11-03)

- Reopen existing workbooks after deploying plugin v11; its versioned URLs bypass the Document Server's immutable asset cache. Deploy the complete sheet-access directory and refresh its gzip files (the local startup script already does this). The context-menu lifecycle event uses the installed SDK's attachEvent route. Owners, ADMIN and authorized managers also have Lock/Unlock selected cells buttons. The plugin reads the selection through the public API. EAC patches standard worksheet protection and cell styles in the XLSX package, creates a version, closes the old editing session and reopens the workbook. No private editor access or sandbox changes are used.
- Share / manage access offers Allow employee to download the original or saved file. Off blocks original/current/history downloads, password exports, file copies, native Office download/print/copy, and guest-link delegation by restricted managers. Folder denials inherit and override another allowed grant. Owners/ADMIN retain their existing authority. Existing copied/downloaded bytes and screenshots cannot be revoked. Other formats whose browser preview requires original bytes cannot be previewed under this restriction.
- Existing grants retain downloads by default. Apply additive MySQL migration V17__file_share_download_restriction.sql before the deployment; local schema update creates its default-false download_blocked column. Communication backup/recovery preserves this flag. The normal file backup recovery still creates private copies without replaying old permissions.
- Both employee pickers call /api/employee/file-sharing, the project's employee API projection; the sheet picker uses policy metadata only for authorization capabilities and mandatory owner/ADMIN rows. No production demo records were added.
- Active EAC Office clients recheck download policy on their heartbeat and close the native editor when it changes; reopen to apply fresh signed permissions. Apply restrictions before employees open the file.

Cell protection requires a synchronized saved workbook and no other editing contributors in the current session. Unsaved changes request a checkpoint and block replacement until it completes. Wrong passwords and stale versions preserve the original. Standard sheet passwords are stored only as Excel protection hashes in the workbook, never as plaintext EAC settings. These locks prevent accidental editing; use Office password encryption for offline confidentiality.

### Encrypted save verification and force-save locking (2026-11-03)

Password-encrypted Office files are OLE containers, not plain ZIP files. EAC now asks an authorized owner/manager to use Verify file password in the editor toolbar. The password is checked against the pending encrypted output (or current encrypted original), encrypted in the database after verification (updated 4 November 2026); its stable APP_FILES_PASSWORD_KEY stays outside the database. The decrypted bytes still pass macro/format validation and the full employee-sheet checkpoint policy. The stored version remains encrypted and unchanged; no password is removed. Wrong passwords or mismatched sheet rules cannot replace the last saved version. Verified passwords now survive backend restarts; an expired in-memory cache reloads the encrypted record automatically. Keep the native editor open while verifying and retry Save workbook afterward.

Force-save requests use an unlocked file read, so an ONLYOFFICE callback can acquire the workbook row lock while the command is running. The cell-lock controller performs its save preflight before the separate patch transaction starts. Timeouts report that save status is unconfirmed rather than claiming data was saved or lost.

Weekend settings accept both legacy CSV (0,6) and JSON ([0,6]); Sunday remains 0 and Saturday remains 6.

## Permanent remembered opening passwords — 4 November 2026

V18 adds file_office_passwords. Only a successfully verified document opening password is encrypted into this table using AES-256-GCM, a random nonce and document-id-bound authentication. Plaintext is never returned by an API. Owners/authorized managers can verify a changed document password, replacing its remembered secret. A cold backend reloads it automatically; the 30-minute in-memory cache is no longer an expiry of the verified password. Purging a document cascades its encrypted credential record. Existing Office file encryption, cell protection and employee ACLs remain in effect.

APP_FILES_PASSWORD_KEY is generated once in the ignored local .env.local, and must remain stable. Set a separate stable key in the NAS private environment; the Synology override requires it. Preserve this key separately from database backups and keep it out of Git. Restoring the database and the same key restores remembered passwords. If a key is lost or intentionally changed, an authorized user can verify each known opening password again. No previous transient password can be recovered from a stopped backend: verify once after this upgrade to persist it.
